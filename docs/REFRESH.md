# Refresh an existing managed vault

Thread 13 adds public `sync` for an explicitly configured managed vault created
with private refresh evidence. Examples here are fictional. See the
[quickstart](QUICKSTART.md) for a new offline build; real Salesforce operations
still require separate authorization. Internal Python interfaces are not stable APIs.

```sh
obforce sync --config "/absolute/path/Fictional Workspace/obforce.toml" --dry-run
obforce sync --config "/absolute/path/Fictional Workspace/obforce.toml"
# Equivalent module entry point:
python -m obforce sync --config "/absolute/path/Fictional Workspace/obforce.toml"
```

All commands are noninteractive. `--config` is required, invocation-relative or
absolute; its source/vault/template paths remain config-relative. Native explicit
paths with spaces are supported. There is no config/home/vault/auth/default-org/
executable discovery. No source-mode/workspace/org rebinding, adoption or force mode.
Build remains initial-only, absent/empty-only and refuses repeats. Sync does not
create a missing vault or reconstruct state. Pending recovery evidence blocks sync.

## What refresh changes

Refresh applies only validated generated-property and generated-region patches.
User prose, supported YAML/comments, tags, aliases and every `technical_debt*`
property remain user-owned. Technical debt is never inferred. Creation templates
apply only to newly discovered components; an existing note is never regenerated
through a creation template. Invalid creation overrides are irrelevant when there
are no new notes. Generated overrides can invalidate existing generated output.

A uniquely moved managed note keeps its UUID and source key. Both incoming and
outgoing links use the reconciled paths, including affected neighbors whose own
source facts did not change. Duplicate IDs, vanished notes, ambiguous ownership,
unsafe paths/collisions, edited generated properties or exact generated bytes
block the entire batch. A hash match never bypasses those ownership checks.

New notes can be added. No component note is deleted automatically. A component
absent from local/partial/incomplete input retains its exact prior normalized facts
and lifecycle. Relationship refresh retains unconfirmed prior evidence as stale,
with original provenance/coverage. Offline input does not infer dependencies.
Requested live relationships remain partial/unavailable even after clean empty
responses; inventory completeness does not imply relationship completeness.

## Private state and recovery

New builds publish private state-document schema 2 at `.obforce/state.json`, with
embedded evidence schema 1: exact tracked normalized component facts, the accepted
refreshed directed graph and optional declared live inventory scope. NoteState's
schema 1, UUIDs, note/marker schemas, accepted hashes and renderer version 3 remain.
No external program is needed to retain facts between independent CLI runs.

The state is private, unencrypted local data. It can include canonical org/record
IDs and optional previously collected audit display names needed by source hashes.
No Apex body, raw CLI response, credentials, extra source paths or human note
content is added to evidence. Disabling audit-name collection does not guarantee
erasure of names in absent retained records or private recovery before-images.
Do not upload state, generated vaults or recovery material to public tracking.

Evidence is limited to 8 MiB inside the existing 16 MiB state ceiling. All other
state/JSON/graph/render/planner/writer limits apply independently, including 10,000
tracked components, 20,000 edges/40,000 observations and the 128-changed-file/32 MiB
before-plus-after transaction ceiling. Earlier bounds can refuse a smaller batch;
there is no truncation, automatic evidence eviction or partial publication.

Notes and complete state/evidence publish through the same recoverable transaction,
with state last. Full pathname/historical descriptor/birthtime/hash/absence/parent
guards, the continuous owning-handle writer lock, same-filesystem staging and
before-images remain. Journal schema 2 is unchanged. Recovery validates each
state version explicitly; schema-1 journals remain unsupported retained evidence.
There is no atomic filesystem snapshot, atomic multi-file replacement, hostile
editor exclusion or power-loss guarantee. Windows sf execution remains refused.

```sh
obforce recover --config ./obforce.toml
# Select only the operation matching validated evidence:
obforce recover --config ./obforce.toml --rollback
obforce recover --config ./obforce.toml --cleanup
```

Preview is read-only. Precommit rollback restores notes plus the complete prior
state/evidence; committed recovery cleans only proven transaction-owned material.
Intervening edits and ambiguous/incomplete evidence refuse, retaining manual-
resolution evidence. Old schema-2 journals containing legacy state still have
their version-specific recovery path; this does not migrate that vault.

Legacy state-document schema 1 lacks lossless prior facts/graph evidence. Sync,
including dry-run, refuses it with conflict 3 before acquisition. Missing, unknown,
corrupt or contradictory state/evidence also refuses. Existing notes and recovery
remain intact. There is no automatic upgrade, bootstrap or adoption. A separate
new empty destination can be built, without automatic transfer of old human
content or a claim that old UUID continuity was preserved.

## Live inventory scope and missing components

Live build/sync retain the accepted explicit live-only `--org` override and require
absolute `--sf-executable` and existing neutral `--sf-directory` paths. The adapter
independently verifies actual org identity against saved state before inventory.
Tests use mocks; these examples do not authorize real operations.

```sh
# Planned target/executable placeholders: substitute only after live authorization.
obforce build --config ./live.toml --sf-executable /fictional/bin/sf --sf-directory /fictional/neutral --inventory-scope-id fictional-reader-v1
obforce sync --config ./live.toml --sf-executable /fictional/bin/sf --sf-directory /fictional/neutral --inventory-scope-id fictional-reader-v1 --attest-comparable-inventory --dry-run
```

The optional build-time scope ID is a logical label of 1–128 ASCII letters,
digits, underscores or hyphens, not an account name or permission fingerprint.
It becomes an immutable reference bound to saved org/Selection and actual inventory
method/API version. A build without it stores no scope reference and can still
refresh safely with absence preservation. Sync cannot add/change that declaration;
no scope-rebaseline operation is implemented. Offline rejects both scope options.

On each sync that should evaluate absence, supply the matching explicit scope ID
and `--attest-comparable-inventory`. This asserts that accessible inventory scope
remained comparable from the declared build through all retained observations,
including intervening partial scans. It is your attestation, not automatic
permission verification. No principal/permission/auth query is added. Alias,
verified org ID, token equality and query success alone do not prove continuity.

Marking missing additionally requires the supported live inventory method,
unchanged Selection/method/API-version, complete exhausted/no-limit/no-warning
inventory and independently verified matching org. A complete attested empty scan
can mark all tracked notes missing while retaining them. Missing means not observed
in the selected accessible scope, not proven deletion. Positive same-source current
observation can reactivate a previously missing note without absence attestation.

Without comparability, absent lifecycle/facts/stale edges are preserved; a completed
live refresh with absent tracked keys returns at least 4 and reports unavailable
missing evaluation. Partial/unavailable scans also preserve absences. Required
acquisition failure returns operational 1 without publishing a candidate. Changed/
ambiguous source/org/workspace/Selection or declared scope/method/API reference
blocks the complete batch with 3; malformed options use 2. Scope attestation never
turns platform relationships into complete coverage.

## Preview, no-op and outcomes

Dry-run validates the complete candidate in memory and creates no config, vault,
state, lock, journal, log, cache or staging artifact. No-op preserves exact note
and state bytes/mtimes, even after human-only edits or with differently formatted
valid state JSON. Ordinary reads can affect access times. An authorized live
preview can cause sf's own auth/config/cache side effects as documented in
[the transport contract](SF_CLI.md); Obforce previews create no artifacts.

First stale/coverage/path changes can legitimately update generated content or
state; repeating unchanged observations stabilizes. No timestamp or persistent
attestation flag is written just to record a check. A valid no-op can return 4
for requested incomplete coverage. Exit precedence remains **3, 2, 1, 4, 0**:
conflict/recovery, invalid input, operational failure, completed incomplete result,
complete/no-op. Reports expose bounded categories/counts/coverage, not private facts.

## Dashboard refresh (Thread 14)

Sync now includes a protected [native Apex Classes dashboard](DASHBOARDS.md).
Valid Thread 13 evidence-bearing vaults add it only when the destination is
absent; no existing file is adopted. Notes and corresponding state retain their
accepted source/graph/ownership contracts. Dashboard edits, missing/moved files,
ambiguity or collisions block the whole batch. Its exact saved baseline uses an
optional dashboard-schema-1 record inside state-document schema 2, while evidence
schema 1, NoteState schema 1 and journal schema 2 remain. MTF-2 advances only the
renderer fingerprint to version 4 for available UTC audit date projections.
Dashboard changes share publication, rollback, committed cleanup and no-op/preview
guards with notes/state. Older executables refuse the extension; use this version
for these vaults and recovery. Legacy evidence-less sync still refuses.

The MTF-2 table update replaces only a clean exact saved dashboard baseline.
Existing human debt/status/severity/review fields are never renamed or backfilled;
new-note Boolean/blank defaults do not authorize whole-note recreation. Human
Boolean decisions remain preserved. New reserved
`sf_created`/`sf_last_modified` dates patch only after both generated baselines
validate. Edited generated dates block the entire batch like all reserved fields.
